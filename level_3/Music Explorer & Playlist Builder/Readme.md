# Music Explorer & Playlist Builder
#### Video Demo: <URL HERE>
#### Description:

Music Explorer & Playlist Builder is a command-line Python application that lets a user search for songs using Apple's public iTunes Search API, browse the results, build a personal playlist from those results, and save that playlist to disk as a JSON file so it can be reloaded and continued later. I built this project to practice working with an external web API, handling real-world JSON data, and structuring a small but complete interactive program with a persistent data format, all while keeping the core logic cleanly separated from user input/output so that it could be thoroughly unit tested.

## How it works

When you run `python project.py`, the program greets you and presents a simple numbered menu with five options: search for songs, view your current playlist, save your playlist, load a playlist, and exit. Searching prompts you for a keyword (a song title, artist name, or both), sends that keyword to the iTunes Search API, and prints back up to ten matching tracks, each shown with its title, artist, album, and duration in a `M:SS` format. You can then type the number of a track to add it to your in-memory playlist; the program prevents duplicate entries by checking each track's unique `trackId` before appending it. Viewing your playlist lists every track you've added so far along with the combined running time of the whole playlist, calculated by summing each track's duration and re-formatting the total (switching to an `H:MM:SS` format automatically if the playlist runs an hour or longer). Saving writes your playlist to a JSON file (`playlist.json` by default, though you can specify any filename), and loading reads a previously saved file back into memory, replacing whatever is currently loaded. The program is designed never to crash on bad input: invalid menu choices, empty search queries, and missing playlist files are all handled gracefully with a friendly message rather than a traceback.

## Files

- **`project.py`** contains all of the program's logic. `main` implements the interactive menu loop described above. Beyond `main`, there are seven additional functions:
  - `search_tracks(query, limit=10)` sends the actual HTTP request to the iTunes Search API using the `requests` library and returns the list of matching tracks as Python dictionaries. It raises a `ValueError` if given an empty or whitespace-only query, and lets `requests.RequestException` propagate upward so `main` can catch connectivity problems specifically.
  - `format_duration(milliseconds)` converts a raw millisecond duration (the unit the iTunes API reports track lengths in) into a human-readable `M:SS` string, raising `ValueError` for negative input.
  - `format_track(track, index=None)` turns a single track dictionary into a one-line, human-readable summary, optionally prefixed with a list index. It falls back to sensible placeholder text ("Unknown Title", "Unknown Artist", etc.) for any missing fields, since not every track returned by the API has complete metadata.
  - `add_to_playlist(playlist, track)` returns a *new* list with the given track appended, unless a track with the same `trackId` is already present, in which case it returns the original list unchanged. It deliberately doesn't mutate the list it's given, which makes it easier to reason about and test.
  - `calculate_total_duration(playlist)` sums the `trackTimeMillis` values across an entire playlist and formats the total using the same logic as `format_duration`, but extended to include hours when needed.
  - `save_playlist(playlist, filename="playlist.json")` serializes the playlist to a human-readable, indented JSON file.
  - `load_playlist(filename="playlist.json")` reads a playlist back from a JSON file, returning an empty list rather than raising an exception if the file doesn't exist or contains invalid JSON — this keeps `main` simple, since "no playlist yet" and "corrupted file" can both be treated the same way from the caller's perspective.

- **`test_project.py`** contains automated tests, written for `pytest`, covering six of the functions above: `format_duration`, `format_track`, `add_to_playlist`, `calculate_total_duration`, `save_playlist`, and `load_playlist`. I deliberately designed most of these functions to be "pure" — taking plain data in and returning plain data out, with no network calls or hidden state — specifically so they could be tested quickly and reliably without needing a live internet connection or a mocking framework. The two functions that do perform file I/O, `save_playlist` and `load_playlist`, are tested together using pytest's built-in `tmp_path` fixture, which provides a temporary directory that's automatically cleaned up after the test runs, so the tests never touch or depend on any real file on disk. `search_tracks`, which is the only function that makes a real network request, is intentionally left untested by `test_project.py`, since testing it meaningfully would either require a live internet connection (making the test suite flaky and slow) or a mocking library to fake the API response; I judged that the other six tested functions already exceed the assignment's requirement of at least three tested functions, so I chose to keep the test suite fast and dependency-free instead.

- **`requirements.txt`** lists the one third-party package this project depends on: `requests`, which is used to make the HTTP call to the iTunes Search API.

## Design decisions

I chose the iTunes Search API specifically because it requires no API key or authentication of any kind, which meant anyone running this project wouldn't need to sign up for a developer account or manage secret credentials just to try it out. This also simplified `requirements.txt`, since no API-client library beyond `requests` itself was needed.

I chose to represent the playlist as a plain Python list of the raw dictionaries returned by the API, rather than converting them into a custom class. This was a deliberate simplicity trade-off: a `Track` class might have been more "proper" object-oriented design, but it would have added a layer of indirection without adding much value for a project this size, since the dictionaries already carry all the fields I need directly from the API's own response format. Saving them straight to JSON was then trivial, with no custom serialization logic required.

Another decision worth mentioning is that `add_to_playlist` returns a new list rather than mutating the one it's given. I went back and forth on this, since in-place mutation would have been slightly more familiar to write and call. But returning a new list makes the function's behavior more predictable and easier to test in isolation — a test can compare the original list against the result to confirm nothing was silently changed underneath it, which is exactly what `test_add_to_playlist` does.
